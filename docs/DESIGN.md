# Design & protocol notes

This document explains how the app is put together and, in detail, how it talks
to an Apple TV. It's aimed at whoever has to debug or extend the protocol layer.

## Why this shape

The SP-01 is a low-power AOSP device with a 2.8" 480×640 screen and no Google
services. That drives a few decisions:

- **View-based UI, not Compose** — lighter on the MediaTek MT8766, trivial to lay
  out for a tiny screen.
- **BouncyCastle lightweight crypto, not JCA/GMS** — identical behaviour on every
  Android level, no provider surprises on a GMS-less ROM.
- **Everything network/crypto is pure JVM** — the whole `companion` package has no
  Android imports, so it compiles and unit-tests off-device (which is how the
  crypto was verified).

## Layered architecture

```
ui/            Activities + views. Owns the keypad while foregrounded.
  │  RemoteAction
  ▼
remote/        KeyMapper, RemoteController, discovery, credential storage.
  │  HidCommand / MediaControlCommand
  ▼
companion/     Companion protocol + HAP pairing. Pure JVM.
```

`RemoteAction` is the seam: the UI/keymap side never mentions Apple or Companion,
and the protocol side never mentions Android. That makes the keymap testable and
the protocol reusable.

## Key capture

The remote screen (`RemoteActivity`) overrides `onKeyDown/onKeyUp/onKeyLongPress`:

- Keys **without** a long-press meaning fire on **key-down** (snappy).
- Keys **with** a long-press meaning (`Back`, `#`, `5`) use
  `event.startTracking()` and resolve on key-up (short) or `onKeyLongPress`
  (long), so a hold and a tap are cleanly distinguished.
- `Back` short-press = Apple TV **Menu**; **hold** `Back` exits and releases the
  keypad. Volume keys are consumed so the phone's own volume UI doesn't appear.

## Companion protocol

The Companion link is a TCP stream of length-prefixed frames:

```
[frameType:1][length:3 big-endian][payload]
```

Once a session is encrypted, `payload` is ChaCha20-Poly1305 sealed (16-byte tag
appended, included in `length`) with the 4-byte header as AAD and a 12-byte
little-endian counter nonce that increments per direction.

Payloads are **OPACK** dictionaries. Requests carry an `_x` transaction id so
responses (which may arrive out of order) can be matched; events are pushed with
`_t = 1`.

### Pair-setup (SRP-6a, run once)

Carried in `PS_Start`/`PS_Next` frames; the payload is a TLV8 blob under key
`_pd`. Group is 3072-bit, hash SHA-512, username `"Pair-Setup"`, password the PIN.

```
M1  →  {Method:0, SeqNo:1}                          "please show a PIN"
M2  ←  {Salt, PublicKey(B)}
M3  →  {SeqNo:3, PublicKey(A), Proof(M1)}           proves we know the PIN
M4  ←  {Proof}
M5  →  {SeqNo:5, EncryptedData}                     our Ed25519 identity, sealed
M6  ←  {SeqNo:6, EncryptedData}                     the TV's identity + LTPK
```

The result is `HapCredentials(ltpk, ltsk, atvId, clientId)` — stored, and wire
compatible with pyatv's credentials string.

Byte-exactness details that matter (and are reproduced deliberately):
- Hashed integers use **minimal-length** big-endian; `u` and `k` use values
  **padded** to N's width (384 bytes).
- The SRP client private `a` is the raw Ed25519 seed.
- `K = SHA512(S)`; keys are derived with HKDF-SHA512 and specific salt/info
  strings (`Pair-Setup-Encrypt-Salt`, …).
- Setup AEAD uses fixed nonces `PS-Msg05` / `PS-Msg06`, left-padded with 4 zero
  bytes to 12.

### Pair-verify (every connection)

Carried in `PV_Start`/`PV_Next`. An ephemeral X25519 exchange, the TV's identity
checked against the stored `ltpk` via Ed25519, then both sides derive the stream
keys:

```
output_key = HKDF-SHA512(salt="", info="ClientEncrypt-main", ikm=shared)
input_key  = HKDF-SHA512(salt="", info="ServerEncrypt-main", ikm=shared)
```

From here the connection is encrypted.

### Session handshake

Before tvOS accepts input the client sends `_systemInfo`, opens `_sessionStart`
(`com.apple.tvremoteservices`), and best-effort `TVRCSessionStart`. Then buttons
work.

### Input

- Button: `_hidC` request `{_hBtS: 1|2 (down|up), _hidC: <code>}`. A press is
  down then up. HID codes: Up=1, Down=2, Left=3, Right=4, Menu=5, Select=6,
  Home=7, VolumeUp=8, VolumeDown=9, Siri=10, PlayPause=14, …
- Skip: `_mcc` media-control `SkipBy` with `{_skpS: ±15.0}` (float — OPACK rejects
  negative ints).

Commands flow through a single coroutine channel in `RemoteController`, so rapid
key presses reach the TV in order and never overlap on the wire.

## Testing strategy

The crypto/serialization can't be "eyeballed" — a wrong byte just makes the TV go
quiet. So the deterministic pieces are pinned to reference vectors generated by
the libraries the format originates from (pyatv, srptools, `cryptography`) and
checked in `CompanionCryptoTest`. Encoder output is additionally confirmed to
decode cleanly under pyatv, i.e. it's valid OPACK a real device will accept.

What's *not* covered automatically: the live TCP/mDNS choreography against real
tvOS. That's the remaining on-device step; this doc plus pyatv's `atvremote
--debug` are the tools for it.
